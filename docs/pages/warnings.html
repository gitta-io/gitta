Warnings and sync

A warning tells an agent that its work and another agent's work affect each other, so the agent can adapt while that is still cheap. Sync brings other work into an agent's copy when you ask for it.

When a warning arrives

An agent gets the warning at its next step, and the check takes about 0.2 seconds. This is also true when a person or a tool without gitta edits the other workspace. A new file that nobody has added yet shows up in gitta status at once, and at an agent's step within five minutes.

gitta knows the common security controls of each language. When one agent removes or switches off a control, and another agent's new code calls the code that the control protected, both agents get a security warning at their next step. What gitta treats as a security control

gitta knows the common security controls of Python, TypeScript and JavaScript, Java and Kotlin, C#, Go, Rust, C and C++, and COBOL with gitta Enterprise. They are login and permission checks, CSRF protection, rate limits, input validation, HTML escaping and certificate checks, written as decorators, attributes, annotations, guards or middleware. Functions whose names say that they check, authorise, verify, validate, sanitise or escape count too. JCL, REXX, COBOL and assembler also have their own rules for one agent’s changes, see Security checks on mainframe code.

What counts as weakened

  • The check is removed or renamed.
  • A control is removed from a function, method or class, or is changed to a comment.
  • An opening is added, such as a CSRF exemption, access for anyone, HTML escaping turned off or certificate checks turned off.
  • A check function gets an early way through, or it loses a refusal.
  • A parameter that sets how strict a check is now defaults to off.

Other changes to a check, for example new parameters, stay normal warnings about a changed function. gitta adds that the symbol is a security check. A stricter check, a new check or an unrelated edit in an auth module gives no security warning.

Mark your own security checks

Put the symbols and paths that gitta must treat as security checks in a file .gitta-security at the top of the repository, one on each line. Commit it, so the whole team and CI use it.

# .gitta-security app.main.routes.edit_profile app.auth.* app/api/auth.py

A line with / or a file name is a path. Other lines are symbols, as gitta names them in warnings. * matches any text. You can also add patterns to one checkout only with gitta init --security PATTERN. An agent that removes a line from .gitta-security is reported as a weakened check.

Risky code in an agent's own change

gitta also checks the lines that an agent adds for well-known security risks. It looks only at the agent's own changed files, and only at lines that are new. Code that was already there is never reported, and a line that only moved is not new. The check takes a few milliseconds, so the agent hears about a risk at the next step, while it still has the code in front of it.

Allow a reviewed line

When a person has checked a line and it is fine, mark it with a comment on the same line. Give the rule and a reason:

row = db.session.execute(sa.text(f"SELECT username FROM user WHERE id = {int(id)}")).first() # gitta: allow sql-text id is cast to int

gitta then reports the allow instead of the note:

$ gitta land user-count gitta: allowed sql-text at app/main/routes.py:92 (id is cast to int) gitta: landed user-count as 86711c470c

To allow a rule for whole paths, add a section to the committed .gitta-security file. Each line names the rule, a path pattern and the reason:

# .gitta-security [allow] shell-text app/cli.py the language code comes from the developer running the command

Every allow that is used is recorded in the audit trail as security_allowed, with the reason. An allow that the agent adds in its own change silences the note, and gitta still reports that the agent added it.

Where warnings appear

  • In the agent's own session. Claude Code gets them through hooks, Cursor and Codex through gitta_status.
  • In the terminal with gitta status. Add --json for scripts.
  • In the output of git merge, git pull and git push to the protected branch, and in the CI log. A fast-forward is checked before the branch moves, so the output comes before git finishes.
  • Live in the terminal with gitta watch, and as plain lines in .gitta/gitta.log.

An agent sees each warning once. gitta does not repeat it at every step, and the repair note after a failed merge comes once per attempt.

Sync

Sync from main brings in work that was merged since the agent started:

$ gitta sync ci99 gitta: merged 2 file(s) from main into ci99: bench/aidev-replay/analyze.py, bench/aidev-replay/test_wilson.py gitta: note: ci-level was merged into main and changed `wilson`, which ci99's new code in bench/aidev-replay/analyze.py calls. ci99 now has the new version. Check that bench/aidev-replay/analyze.py still works with it. The tests on the combined code decide when it is merged.

Sync is all or nothing. If one file cannot be merged, no file changes, and gitta names the file. The agent's own changes are always kept.

Automatic sync

gitta syncs the workspaces it made itself, with gitta run or gitta up, from main at each agent step, when the work merges cleanly and nothing their new code uses changed meaning. A worktree made by Claude Code, Cursor, Codex or git worktree add keeps exactly what its agent wrote. git brings main in when the agent merges, and the tests at merge time decide. To turn automatic sync off, set "auto_sync": false in .gitta/config.json.

Test a combination

gitta check runs your gate on an agent's work combined with each other agent's work. It does not change any worktree. You run it when you want to. gitta never runs it for agents, because the merge runs the tests.

$ gitta check ci99 gitta: ci99 + ci-level: BREAKS File "/Users/you/src/gitta/.gitta/wt/check-0/bench/aidev-replay/test_ci99.py", line 7, in test_wider lo, hi = ci99(50, 100) ~~~~^^^^^^^^^ File "/Users/you/src/gitta/.gitta/wt/check-0/bench/aidev-replay/analyze.py", line 35, in ci99 p, lo, hi = wilson(k, n, 2.576) ~~~~~~^^^^^^^^^^^^^ TypeError: wilson() takes 2 positional arguments but 3 were given ---------------------------------------------------------------------- Ran 2 tests in 0.001s FAILED (errors=1)

Add --with AGENT to test against one agent only, and --json for scripts. Results are PASSES, BREAKS, DOES_NOT_MERGE or CANNOT_RUN. CANNOT_RUN means a tool that the gate needs was not found, so the tests did not run. That is a setup problem for you to fix, and agents are not told that their work breaks. Checks run in parallel. Use gitta init --parallel N to limit how many run at once.

Claims

Before a large change, an agent can claim the symbol or path. Others are warned before they build on it. gitta releases an agent's claims when gitta land merges its work, or when its worktree is removed.

$ gitta claim ci-level bench.aidev-replay.analyze.wilson "making z keyword-only" gitta: ci-level claimed bench.aidev-replay.analyze.wilson $ gitta release ci-level bench.aidev-replay.analyze.wilson gitta: ci-level released bench.aidev-replay.analyze.wilson
